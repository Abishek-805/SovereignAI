# Smart Router V2 live development audit

Source: `benchmarks/smart-code-router-v2-continuation.json` (running checkpoint). This is a read-only audit of observed development cases. Counts below are a snapshot after 83 completed rows; they will change as the suite continues. No held-out fixture or result was inspected.

## Observed checkpoint

- State `RUNNING`; 83 completed rows, all pinned arm A (Gemma 4 E2B). Arm B–E outcomes are not yet observed, so comparative routing or quality claims are unavailable.
- The 20 explanation rows have no executable artifact oracle. They must remain `correctness=UNKNOWN` and `goal_satisfied=UNKNOWN` until an independent semantic review. Their model responses alone establish neither correctness nor task completion.
- Among 20 edit rows, 13 staged candidates passed independently supplied trusted tests in Docker. These are `READY_FOR_REVIEW`, with `target_committed=false` and `publication=NOT_ACCEPTED`; passing validation does not mean the project files were accepted or published. Three edits (`v2-main-023`, `038`, `039`) failed before candidate testing: two `generation_format`, one `semantic_uncertainty`. Four edits failed actual Docker validation, generated repair attempts, and failed Docker validation again.
- For `v2-main-025`, trusted test exit codes were `[1, 1]` with distinct candidate SHA-256 values `a9fea139…` and `ac985a46…`; state `failed`, `supervisor_attempts=2`, `repair_count=1`, `repair_stop_reason=repeated_failure`. `v2-main-033` likewise recorded `[1, 1]`, two distinct candidate hashes, and the same stop reason. `v2-main-035` and `040` recorded `[1, 1]` and identical candidate hashes across attempts, then stopped. The tests are independently supplied; the candidate did not rewrite their recorded trusted hashes.
- **One actual repair passed:** `v2-main-045` (debug) generated candidate `93dd4f3d…`, failed an independently supplied trusted Docker test (exit 1), generated a different candidate `fbf4f5df…`, then passed the same trusted test (exit 0). The result records `supervisor_attempts=2`, `repair_count=1`, `repair_stop_reason=validated`, and `READY_FOR_REVIEW`; `publication=NOT_ACCEPTED`. This proves the bounded repair path worked for this particular pinned Gemma case, not that V2 routes repair to Coder or that the patch was published.
- Debug cases `v2-main-047`, `048`, and `052` each recorded two actual trusted Docker failures `[1, 1]` and stopped after one repair. Case `050` failed before Docker as a `MODEL_FAILURE`. At 83 rows, the taxonomy has 19 `VALIDATION_FAILURE` and eight `MODEL_FAILURE` rows. The remaining rows have no recorded failure layer; this alone is not a semantic pass claim.
- The first multifile refactors expose a concrete quality limit. Cases `v2-main-076` and `077` each edited `solution.py` and `legacy.py`, generated three distinct candidate pairs, and ran the same independently supplied trusted test in Docker three times. Every test failed (`[1, 1, 1]`), despite 36 and 28 model calls and 129.6 and 111.6 seconds respectively. Case 076 stopped at `attempt_budget` (three supervisor attempts, two repairs); 077 stopped at `repeated_failure` (three attempts, two repairs). Cases 078 and 079 failed twice (`[1, 1]`) and stopped at `repeated_failure`; case 080 failed three times (`[1, 1, 1]`) and also stopped at `repeated_failure`. All five record `original_sources_preserved=true`, `target_committed=false`, `completion=failed`, and `publication=NOT_ACCEPTED`; there is no evidence of a published incomplete refactor.
- Case `v2-main-081` has a mixed sequence: an initial two-file candidate failed a trusted Docker test (exit 1), followed by a `semantic_uncertainty` model proposal failure. Its row is classified `MODEL_FAILURE` and `repair_observed=false`, with no supervisor retry counts. Accordingly, those two summary fields undercount sequences that reached Docker but failed during a later proposal. The recorded failure message says the proposed `solution.py` logic and `legacy.py` compatibility import did not satisfy the request. No publication was recorded.
- Case 082 added another `[1, 1]` trusted Docker failure with `repeated_failure` stop and original source preservation. Case 083 failed before Docker as `MODEL_FAILURE`. No multifile case through 083 has independently passed its trusted tests.
- Two runtime load/switch observations occurred in arm A: case 001 moved from resident Coder to Gemma (5.52 s); case 029 had no resident model and loaded Gemma (7.31 s). Both list `effect=UNKNOWN`, which is correct until an equivalent paired outcome is available. No repair-stage worker switch was observed. The maximum sampled `llama-server` process count was one.

## Outstanding evidence

The running comparison still needs arm B–E, especially V2 arm E, before we can evaluate whether a failed generated candidate moves to Coder, repairs using actual feedback, and passes independent validation. Arm A now shows one repair-to-pass and 19 failed validation outcomes. A paired analysis must establish whether each load or switch helped. Exact publication requires a separate Accept observation; this benchmark stages work and intentionally does not accept it.
