# Code execution and publication boundary

Generated Code and Agent edits are staged under the workspace task metadata, outside the canonical project. Generation, review, and Discard do not publish those bytes. Accept rechecks the expected SHA-256 revisions and staged hashes under the workspace mutation lock, then publishes the listed paths. Publication requires `container_executed` from a verified Docker run; when Docker is unavailable, Accept fails and the draft remains staged. A Python exception during publication triggers best-effort rollback of paths already written.

The Linux runner starts a disposable, non-root container by pinned image ID. It binds only the selected execution input read-only, uses a read-only root filesystem, drops capabilities, disables network, applies CPU/memory/PID/file-size limits, and creates a 384 MiB `/output` tmpfs. The backend collects at most eight top-level output files of at most 1 MiB each, then removes the container. A 300-second parent process bounds cleanup if the backend crashes after container start. This is an isolation boundary for execution, not a claim of immunity to Docker or kernel vulnerabilities.

Known limitations: multi-file publication is not crash-atomic across Windows filesystem writes, and external programs can race the in-process revision check. The in-process lock coordinates SovereignAI requests only. Agent file move/copy/delete and folder creation now use a staged review protocol; existing folders are reused and destination files can be replaced only after review, a Docker smoke run of the resulting snapshot, and revision checks. This smoke run confirms the sandbox accepts the planned files; it does not re-test the behavior of unchanged code. User-initiated Code workspace file controls and terminal project synchronization remain direct writes, outside the AI edit publication gate. Knowledge document mutations have their own application workflow and are not covered by the code publication gate. Do not use these guarantees as a substitute for host backups or operating-system permissions.

The live verifier in `scripts/verify_docker_sandbox.py` records image ID, policy fingerprint, verifier version and timestamp only after all probes pass. The backend rejects missing, stale (over 24 hours), or source-mismatched records. Re-run the verifier after changes to the runner, image recipe, or verifier.
