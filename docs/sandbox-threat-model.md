# Sandbox threat model

Untrusted inputs are model-generated source, user-entered project source, stdin, terminal commands, project filenames, and generated outputs. A malicious program may try to read host secrets, cross into another project, exhaust disk/CPU/memory/processes, contact the network, or escape the container. The expected trust boundary is a temporary Docker Linux container with one read-only input tree and one bounded writable tmpfs. The backend is trusted and remains a higher-value target; compromise of Docker Desktop, the Linux kernel, or backend process is outside the runner's enforceable guarantees.

The input mapper validates relative paths and excludes common secret paths such as `.env*`, `.git`, cloud credentials, private keys, and SSH directories. This is defense in depth; it is not a general secret scanner. Output collection accepts a small fixed set of top-level files. Canonical publication is a separate backend action following validation and revision checks. The UI must not treat an unvalidated draft as saved project code.

Reviewed publication now uses the durable journal in `workflows/publication_journal.py`, integrated through `workflows/coding_workspace.py`. Backups, original and accepted hashes, explicit directory actions and transaction identity are persisted before canonical application. Startup and mutation-entry recovery restore only transaction-owned exact bytes, preserve unexpected external bytes, and mark `recovery_required` when automatic recovery would overwrite or remove newer content. That state blocks guarded project mutations pending user comparison and resolution. Undo uses the same transaction controller. See [publication architecture](publication-architecture.md).

The OS advisory lock coordinates cooperating SovereignAI writers sharing one workspace metadata root. It does not coordinate external editors or commands. An actor with host filesystem permissions can still change a file or swap a parent after the repeated path/revision checks and before an OS operation. Symlink, junction and reparse checks reject detected linked paths, but they do not constitute a Windows handle-based compare-and-swap. Intermediate files may be visible during a multi-file transaction; process interruption can leave partial changes until recovery runs.

File contents and journal temporaries are flushed and synced before atomic replacement. Portable Python does not sync Windows directory entries here, and storage caches/filesystem behavior limit what this establishes under power loss. Process-crash recovery tests are not forced-power-loss tests. Recovery metadata and backups are trusted host-controlled state; a host actor who can modify the backend or its metadata is outside the untrusted-container boundary.

Residual execution risks include Docker/kernel vulnerabilities, resource consumption by Docker Desktop itself, and unrecognized secret filenames inside an explicitly selected project. The backend/controller, publication controller and canonical project are trusted; staging is controlled host state; generated/executed code and third-party dependencies are untrusted. VS Code, PowerShell and other host applications are external writers. Manual Code file operations, terminal synchronization, project administration and Knowledge mutations retain separate authorization scopes.

The current release verifier recorded all 18 probes as true in `benchmarks/release-docker-verification.log`: normal execution, blocked network connection, read-only root and input, non-root identity, dropped capabilities, no-new-privileges, process inspection, configured PID/memory/CPU limits, output capacity, absent Docker socket, host environment and project secret exclusion, timeout, cancellation and container cleanup. The verifier binds its successful attestation to image identity, runner/image-recipe/verifier fingerprint, verifier version and timestamp. The backend rejects a missing or mismatched attestation and one older than 24 hours. Runner, recipe or verifier changes require re-verification.

These probes establish the observed tested configuration and negative cases. Cgroup limit inspection is not exhaustive adversarial exhaustion testing. A blocked connection to the probe destination is not proof of every possible network channel. Process inspection is not a container-escape proof. The 18 probes do not independently exercise every cross-project access strategy or secret filename. Docker `--network=none` and the other restrictions reduce the tested attack surface without certifying Docker or the kernel as vulnerability-free.

Additional live probes in `benchmarks/release-isolation-extra.log` verify separate input/output snapshots, denial of a 600 MiB allocation (exit 137), bounded child-process creation, and output-volume exhaustion. The audit initially found that `--memory=512m` alone allowed swap and the allocation succeeded. The runner now also sets `--memory-swap=512m`; fresh verification requires `memory.swap.max=0`. The output pressure probe uses multiple 8 MiB files to exercise the 384 MiB tmpfs separately from the 32 MiB per-file limit. These are specific observed denial tests, not peak host-resource measurements or exhaustive escape testing.
