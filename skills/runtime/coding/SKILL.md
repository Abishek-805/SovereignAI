---
name: coding
description: Create, modify, explain and repair related project code.
---

Resources: supplied file excerpts, project map, immutable workspace snapshot, staged diff, code generator and Docker validation results. Inspect related imports/callers and real entrypoints. Preserve required functions, interfaces and unrelated files. A folder is an output location, not the requested implementation. Repair from the original request, current diff/candidate and exact error; preserve already-correct behavior. Returning an exception object is not raising it. Complete code must implement the requested output behavior. Respect action schemas and the review/publication boundary; do not claim validation based on syntax or model confidence.

Application creation means delivering usable software, not describing how the user could build it. Resolve the requested interface (web, command line, desktop, API) and requested behaviors from the current request. Where unspecified, choose a simple interface supported by the available runtime and state the choice in the plan; do not invent additional product features. A runnable application needs an entrypoint, actual input/action/output behavior, connected supporting files and any necessary dependency manifest. Helpers alone satisfy a library request, not an application request.

The existing workspace plan carries a request contract: deliverable, behavioral requirements and entrypoint. Use it consistently for every generated file. Keep exported symbols, import names, asset paths, data formats and error semantics consistent across the complete planned project. Account for all requested behavior, including invalid input and persistence when requested. Do not substitute an earlier project or copy demonstration subjects. Original current-request wording overrides a mistaken plan or reference history.
Preserve every behavioral qualifier and exceptional case; filenames alone are not a requirements checklist. Validate inputs before special-case returns and ensure shortcuts obey the same constraints as the main path. Do not replace a requested error with a return value or an error message alone. Use supplied acceptance tests and real tool errors as evidence when available. Existing trusted tests must stay unchanged. Use correct entrypoint arguments and check outputs and errors, not just compilation. The existing Docker validator runs available tests; feed its exact failures into the existing repair path. Do not add blanket extra test files to every request or derive expected results merely by copying the implementation's output. Generated tests do not become independent validation because they passed.


Generate the requested implementation yourself through the available code actions. Do not return a promise, tutorial or request for permission when the user has requested creation. Distinguish runnable software from an instruction to launch it now: a CLI requiring arguments cannot be checked by assuming an argument-free invocation. Syntax checking is useful evidence but does not prove the requested behavior works.

The build_contract carries original-request executable obligations. Implement the stated argv, exported interfaces, output and error behavior; do not weaken these obligations to fit the candidate. Independent checks run in Docker. During repair use the failed check, exact invocation and actual output, preserve the retained candidate files, and fix the affected source rather than restarting the project. File/syntax checks alone do not establish behavioral correctness. Unsupported or ambiguous acceptance behavior must remain explicitly unverified.
